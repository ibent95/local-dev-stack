tool profiles added on top of the core stack: **DrawDB** (schema design),
**Apache Hop** + **Apache Superset** + **Metabase** (data warehouse & BI), **Hoppscotch**
(API client / Postman alternative) + **Plane** (project management), **DuckDB** + **Trino**
(analytical query engines), **Semgrep** + **SonarQube** + **OWASP ZAP** + **Trivy**
+ **OpenVAS** (code & vulnerability scanning), **code-review-graph** (AI code intelligence),
**Vaultwarden** (password manager), **Mailpit** (SMTP + inbox), **Penpot**
(design), **Instatic** (visual CMS), **OpenWA** (WhatsApp API), **RustFS**
(file sharing), **HeadlessX** (undetected browser automation), **Playwright**
(End-To-End testing), the **LDS apps** (Analytics, Tasks, Wiki), **ERPNext**

**draw.io** (diagramming), **LLDAP** + **OpenLDAP** (LDAP directories),
**Prometheus** +
**Grafana** (monitoring), and the built-in **LDS Text Diff** + **LDS Palette
Generator** utilities served straight from the control panel. The two
backing-service browsers, `phpcacheadmin` and `dbx`, are documented in
[13 · Profiles](13-profiles.md).


## Control panel — `http://localhost`

The PHP container serves a control panel as its default site, reachable at
**`http://localhost`** (no hosts entry needed). It is generated by
`configs/web/dashboard/index.php` and shows, live:

- **Tools & web UIs**, grouped — *Data management* (phpCacheAdmin, DBX, Kafka
  UI, LDS Kafka connector builder), *File storage* (RustFS), *Documents &
  credentials* (Tasks, Wiki, Vaultwarden), *File conversion* (SnapOtter,
  ImgCompress),
  *Identity (LDAP)* (LLDAP, OpenLDAP), *Messaging / Socials* (Mailpit,
  OpenWA), *Browser
  automation & scraping* (HeadlessX), *Design* (Penpot, DrawDB, draw.io,
  LDS Palette Generator), *Websites &
  CMS* (Instatic), *ERP & business* (ERPNext), *Project management*
  (Plane), *Analytic & Business
  intelligence* (Analytics, Hop, Trino, Superset, Metabase), *Monitoring &
  observability* (Grafana, Prometheus), *Code & security quality
  scanner* (Semgrep, SonarQube, Trivy, ZAP, OpenVAS, code-review-graph), *Testing tools*
  (Playwright, Hoppscotch), *Developer utilities* (LDS Text Diff), and *Websockets monitoring*
  (Centrifugo, MQTTX) — each with a
  ●/○ reachability dot.
- **Projects** — every folder under `${PHP_PROJECTS_PATH}`, linked at its
  `<name>.test` host.
- **Backing services** — MySQL/Postgres/Mongo/Redis/Memcached/Kafka/brokers,
  probed for up/down.
- **Docs** — this handbook, rendered in-browser at **`http://localhost/docs.php`**
  (chapter sidebar, in-page TOC, prev/next, EN/ID switch). The `docs/` tree is
  bind-mounted read-only at `/var/lds-docs` and turned into HTML by
  `configs/web/dashboard/docs.php` + `lib/parsedown.php`, so editing a `.md`
  shows up on the very next request.

> It is served from `/var/lds-dashboard` (mounted **outside** the project path),
> so it is **not** a project — there is no `__dashboard.test`, and it never shows
> up in the project list. The links and groupings here mirror the `lds hosts-sync`
> output.

## Database design — DrawDB

**Profile:** `drawdb` (`LDS_ENABLE_DRAWDB`). **Off by default.**

Browser-based database schema designer / ER diagrammer. A static SPA — diagrams
persist in your browser (no server DB). Upstream image `ghcr.io/drawdb-io/drawdb`
(pinned in `.env`), single lightweight container.

- **Open it at `http://localhost:4502`** — **not** `drawdb.test`.
  DrawDB calls `crypto.randomUUID()`, which browsers expose only in a **secure
  context** (HTTPS or `localhost`/`127.0.0.1`). Over plain `http://drawdb.test`
  that function is `undefined` and the app renders a blank page. Use the
  `localhost` port, or serve the stack over HTTPS (`LDS_ENABLE_HTTPS=true`) to
  use `https://drawdb.test`.

## Data warehouse & BI — Apache Hop, Apache Superset & Metabase

**Profiles:** `hop` (`LDS_ENABLE_HOP`), `superset` (`LDS_ENABLE_SUPERSET`),
`metabase` (`LDS_ENABLE_METABASE`). **Off by default.** All three connect to the
stack DBs as data sources — from inside the network use the container names
(`lds-postgres:5432`, `lds-mysql:3306`).

### Apache Hop — `hop.test`

Browser-based **ETL / data-integration pipeline designer** (Hop Web).

- **Image:** `apache/hop-web` (Tomcat) — **not** `apache/hop`, which is the
  headless `hop-server` and forces HTTP Basic auth (`cluster`/`cluster`).
- **No login.** Served under `/ui`; the app redirects `/` → `/ui` itself, so
  `hop.test` opens straight into the designer. (`/ui` has **no** trailing slash —
  `/ui/` is a 404.)
- **MySQL driver.** Hop bundles many JDBC drivers (Postgres, MSSQL, …) but **not**
  MySQL Connector/J (GPL). It's added via a single-file mount from
  `assets/jdbc/` — see the shared [`assets/jdbc/README.md`](../../assets/jdbc/README.md) to (re)fetch the jar
  (`HOP_MYSQL_DRIVER` in `.env`). Postgres needs nothing; Kafka uses Hop's bundled
  *transforms* (not JDBC); MongoDB/Redis have no JDBC driver.
- **No session timeout.** Hop Web (Eclipse RAP) ties its canvas to the HTTP
  session; we flip Tomcat's default 30-min timeout to *never* so you don't get
  "session timed out" mid-work (a `command` wrapper on the service).
- **Persistence:** two bind-mounted host directories (`data/hop/config`
  and `data/hop/audit`) persist projects, connections, and user
  preferences across container restarts and recreates. Your pipelines and
  workflows live directly on disk — browse, edit, or version-control them
  without touching the container. Only the user-data subdirectories are
  mounted — the Hop application itself always comes from the image, so image
  upgrades work cleanly. Use `down -v` to wipe the directories and start fresh.
- **Folder-per-project.** Scaffold a new Hop project with:
  ```sh
  lds new hop my-etl-project
  ```
  This creates a directory under `HOP_PROJECTS_PATH` (default `data/hop/projects/`)
  with a `project-config.json`, plus `metadata/`, `pipelines/`, `workflows/`, and
  `datasets/` subdirectories. When `lds up hop` runs, the `hop-register` script
  (auto-run post-up) registers each project folder in Hop's `hop-config.json`
  via `hop-conf` inside the container. Your pipelines and workflows live on disk
  — version-control them with git directly.

### Apache Superset — `superset.test`

**BI dashboards & reporting.** Login **`admin` / `admin`**.

- **Image:** Docker Hardened Image `${DHI_REGISTRY}/superset` — the non-dev,
  nonroot (UID 65532) runtime variant.
- **Self-initialises on start** (db upgrade → create-admin → init → gunicorn),
  driven from the image's venv Python since the hardened image has no shell.
- **Metadata** lives in the **shared Postgres** — the `lds_superset` DB is
  created by `POSTGRES_INIT_SPECS`, and `superset db upgrade` builds the schema
  on first start. The `data/superset/` bind mount holds config, cache and the
  folder-per-project YAML exports (Login **`admin` / `admin`**).

### Metabase — `metabase.test`

**Self-hosted BI dashboards** — the simpler, question-first alternative to
Superset.

- **Image:** official upstream `metabase/metabase` (AGPL-3.0), pinned via
  `METABASE_VERSION`. There is no DHI variant.
- **No default login.** The first visit to `metabase.test` opens Metabase's
  setup wizard — create your own admin account and workspace there.
- **Metadata** lives in the **shared Postgres** — the `lds_metabase` DB is
  created by `POSTGRES_INIT_SPECS` (`MB_DB_TYPE=postgres`); Metabase runs its
  own application-DB migrations against it on first boot, so questions,
  dashboards, collections and users survive `down`/`up`. The legacy H2 file
  may still sit under `data/metabase/` but is no longer read.
- **Data sources:** after the setup wizard, add the stack DBs — e.g. Postgres
  `postgresql://app:app@postgres:5432/app` (`postgres`/`mysql` resolve on
  `lds-network` from inside the network).
- Open at **`http://metabase.test`** (or `localhost:4541`). The first boot
  takes ~1–2 minutes (JVM + application-DB migrations); the compose
  healthcheck waits it out before reporting healthy.

## API tooling & project management — Hoppscotch & Plane

**Profiles:** `hoppscotch` + `plane` (`LDS_ENABLE_HOPPSCOTCH` /
`LDS_ENABLE_PLANE`). **Both off by default.**

### Hoppscotch — `hoppscotch.test`

**Self-hosted API client** — the Postman alternative: REST, GraphQL,
WebSocket, SSE and MQTT in the browser.

- **Image:** official `hoppscotch/hoppscotch` AIO (MIT Community Edition),
  pinned via `HOPPSCOTCH_VERSION`. One container in **subpath mode**:
  `/` = the client, `/admin` = onboarding & users, `/backend` = GraphQL/REST —
  all under the single `hoppscotch.test` vhost.
- **Data:** shared Postgres — the `lds_hoppscotch` DB is created by
  `POSTGRES_INIT_SPECS`, and the `hoppscotch-migrate` one-shot runs
  `prisma migrate deploy` idempotently on every `up` (the app waits for it via
  `service_completed_successfully`, the ERPNext-configurator pattern).
  Collections, environments and history survive `down`/`up`.
- **Login:** the `/admin` onboarding picks the auth providers. `EMAIL`
  (magic link, the default) sends through the stack's **Mailpit** — start the
  `mail` profile and click the link in `mail.test`. OAuth
  (GitHub/Google/Microsoft) needs client IDs entered in `/admin`.
- Open at **`http://hoppscotch.test`** (or `localhost:4542`). Point requests
  at your local services by their `.test` host — they resolve through the edge
  proxy like everything else.
- `HOPPSCOTCH_BASE_URL` defaults to `https://` (the edge proxy terminates
  TLS); switch it — and `HOPPSCOTCH_WS_URL` — to `http://`/`ws://` if you run
  the stack without `LDS_ENABLE_HTTPS`.

### Plane — `plane.test`

**Open-source project management** — the Jira/Linear alternative: work items,
cycles, modules, pages, analytics.

- **Images:** official `makeplane/plane-*` (AGPL-3.0 Community Edition),
  channel tag `APP_RELEASE` (default `stable`). This is the **full vendor CE
  stack** (~13 containers): frontend, space, instance admin, live server, API,
  celery worker + beat, a one-shot `migrator`, plus its own caddy edge. The
  migrator re-runs on every `lds up plane` and its exited container is
  auto-removed right after a successful `up` (kept only when migrations
  fail, for `docker logs lds-plane-migrator`).
  Its **DB, cache, broker and object storage are shared**: dedicated
  `lds_plane` database on the shared Postgres (`POSTGRES_INIT_SPECS`), the
  shared Redis (logical DB 0), the shared RabbitMQ broker (`rabbitmq`
  profile), and the RustFS `uploads` bucket.
- **Edge:** the vendor caddy `proxy` service is renamed **`plane-proxy`** (the
  bare `proxy` alias on `lds-network` belongs to the LDS edge router). It
  carries `VIRTUAL_HOST=plane.test`, so the LDS edge proxy routes straight to
  it; it is also published loopback-only at `localhost:4543`.
- **First run:** open `plane.test` and the setup wizard creates the instance
  admin. Change `PLANE_SECRET_KEY` / `PLANE_LIVE_SECRET_KEY` in `.env` before
  sharing the instance.
- **Storage:** Plane-scoped named volumes (`local-dev-stack_{logs_*,proxy_*}`)
  — `lds down -v` wipes them, exactly like the databases. DB data lives in the
  shared Postgres volume, cache in the shared Redis volume, broker data in the
  shared `rabbitmq_data` volume, uploads in the `rustfs-data` volume.

## Code quality — Semgrep

**Profile:** `semgrep` (`LDS_ENABLE_SEMGREP`). **Off by default.**

A static-analysis (SAST) scanner with a self-contained SARIF findings dashboard.
It's two compose services:

- **`semgrep`** (profile `semgrep`, `all`) — the **viewer**: a tiny nginx serving
  `data/semgrep/reports/` at `semgrep.test`. `index.html` is a self-contained
  dashboard over `report.sarif` (no backend): severity tiles, findings-by-rule /
  by-file / category (CWE, OWASP, confidence) breakdowns, facet filters (severity,
  rule, file, tag, search), expandable findings with the code snippet + rule
  description, paging, and **Print report** (the current filtered view, all rows)
  for Save-as-PDF. It also reads `scan-meta.json` for the scan metadata. This is
  what `lds up semgrep` starts.
- **`semgrep-scan`** (profile `semgrep-scan`) — the **scanner**: the pinned
  `semgrep/semgrep` CLI image, declared in compose so it's versioned. It's a
  one-shot, so it lives in its own profile and **never auto-starts** on
  `lds up`/`all` (no lingering Exited container). `lds up semgrep` **pre-pulls**
  this image (best-effort), so the scanner ships with the profile without being a
  running service; or pull it directly with
  `docker compose --profile semgrep-scan pull semgrep-scan`.

Run a scan:

```sh
lds tools semgrep [path]      # default: current dir, rulesets from SEMGREP_RULES
lds tools semgrep clear       # clear current SARIF + metadata from viewer storage
```

That runs the pinned `semgrep-scan` image with `docker run -v <path>:/src` and
writes `data/semgrep/reports/report.sarif` into the folder the viewer serves.
(It uses `docker run`, not `docker compose run`, because Compose's `-v` parser
splits on `:` and chokes on a Windows drive-letter path like `D:\…`.) Refresh
**`semgrep.test`** and the dashboard renders the findings with the last scanned
project metadata and a **Clear** action. No DB; until you run a scan there's no
`report.sarif` to show.

`SEMGREP_RULES` takes **one or more rulesets, comma-separated** — each becomes
its own `--config` flag, which is how you tighten coverage. The shipped default
is **`p/default,p/security-audit`** (security-audit is deliberately noisier);
other useful sets: `p/default,p/owasp-top-ten,p/cwe-top-25` or per-language
packs like `p/default,p/php,p/typescript`. Registry packs (`p/php`, `p/ci`),
rules URLs, and local YAML paths all run with metrics off. `auto` is also valid
but **requires metrics on** (it uploads project metadata to semgrep.dev to choose
rules), and that end-of-run upload can hang on slow/offline links — so the script
only enables metrics when `auto` is among the rulesets. (Registry packs are still
fetched over the network at scan start; that's load time, not a hang.)

Two more knobs: `SEMGREP_SEVERITY` filters what's reported (comma list of
`INFO,WARNING,ERROR`), and **`SEMGREP_ERROR=1`** makes the CLI exit `1` when
findings exist (the report is still written first) — handy for CI gating.

## Vulnerability scanning — OWASP ZAP, OpenVAS & Trivy

**Profiles:** `zap` (`LDS_ENABLE_ZAP`), `trivy` (`LDS_ENABLE_TRIVY`);
`sonarqube` (`LDS_ENABLE_SONARQUBE`) adds code quality. **Off by default.** These
complement Semgrep (SAST, source code):

| Tool | What it scans | How |
|---|---|---|
| **Semgrep** (SAST) | source code, for bug patterns | `lds tools semgrep [path]` |
| **SonarQube** (code quality) | bugs, code smells, duplications, coverage, quality gates | `lds tools sonar [path]` |
| **OWASP ZAP** (DAST) | your **running** `.test` apps (SQLi, XSS, SSRF, auth, …) | browser UI at `zap.test/zap` |
| **OpenVAS** (DAST) | deep vulnerability scans (Greenbone CE companion) | `lds openvas start` → `localhost:9392` |
| **Trivy** (SCA) | containers, filesystems, git repos, dependency manifests | `lds tools trivy [path]` / `lds tools trivy image <name>` |

### OWASP ZAP — `zap.test` / `localhost:4510`

Dynamic Application Security Testing against **live** apps. The full ZAP desktop
UI runs in the browser (WebSwing): start it with
**`lds up proxy zap`** (or `php zap`) — ZAP needs the **proxy** running, which
routes `zap.test` *and* carries the `dns` container behind its in-network DNS
view — then open **`zap.test/zap`** (ZAP's proxy/API port is
`:4512`) and scan a local app with **`http://<folder>.test`** as the target.

- **In-network DNS for free.** ZAP resolves `*.test` through the dns container's
  *in-network* view (`10.99.0.53` on `lds-dnsnet`), which answers `*.test` with
  the **proxy container's IP** — so `http://myapp.test` reaches the right vhost
  from inside the container, while the host-facing dnsmasq still answers
  `127.0.0.1` for your browser. (If the dns container is down, ZAP falls back to
  Docker's embedded DNS — container names + internet still resolve; only `.test`
  apps need the proxy up.)
- **After updating the stack**, rebuild the `dns` image once so the in-network
  view exists: `lds up --rebuild proxy` (or `docker compose build dns`) — a
  stale image keeps the old single-dnsmasq behaviour.
- **ZAP starts lazily:** the first visit to `zap.test` takes a moment while ZAP
  boots inside the UI.
- **Persistence:** ZAP runtime files are bind-mounted in `data/zap/`
  (`/zap/wrk` + `/home/zap`) so certs/session files survive container recreation.
- **Heavy:** Java-based, capped at ~2 GB (`ZAP_MEM_LIMIT`). Start it only when
  you actually scan.
- `ZAP_VERSION` defaults to the rolling `stable` tag — pin a specific version in
  `.env` for reproducibility.

> Scanning needs the target app to be **running** — start the project first
> (`lds up` with its profile), then point ZAP at it.

### OpenVAS — Greenbone CE companion (out-of-stack)

**Not a profile.** The deep DAST alternative, built on Greenbone Community
Edition and managed as an out-of-stack companion:
`lds openvas start|stop|restart|logs|ps|pull` (`configs/openvas/` — its own full
Greenbone stack, ~18 containers, data in `data/openvas/`). Much heavier and
slower than ZAP — ~4+ GB RAM, multi-GB pulls, and the first boot syncs the
vulnerability feeds for 20–60+ minutes — but considerably deeper when you need a
real vulnerability-management scan.

- UI: **`http://localhost:9392`** (login `admin`/`admin`), TLS on `:8943`.
  When the main stack is up the wrapper applies an overlay: the web UI joins
  `lds-network` (so **`openvas.test`** works through the LDS proxy) and the
  scanner joins `lds-network` + `lds-dnsnet` with the in-network `*.test` DNS
  view — so `http://myapp.test` is scannable directly, exactly like ZAP.
- Different scope than ZAP: OpenVAS is a *vulnerability management* scanner
  (CVE feed-driven, targets + credentialed scans); ZAP is a web-app fuzzer.
  Running both is fine.

### Trivy — `trivy.test` / `localhost:4511`

Known-CVE (SCA) scanning of *artifacts*, not live apps: container images,
filesystems, git repos, and dependency manifests (`composer.lock`,
`package-lock.json`, `go.sum`, …). Same two-service pattern as Semgrep: a
viewer (`trivy` — what `lds up trivy` starts) + a one-shot scanner
(`trivy-scan`, in its own profile so it never auto-starts).

```sh
lds tools trivy [path]        # fs scan — directory, repo, or dep manifest
lds tools trivy image <name>  # image scan — e.g. lds/php:8.4 (uses the docker socket)
lds tools trivy clear         # clear current report + metadata from the viewer
```

Writes `data/trivy/reports/report.html`, served at **`trivy.test`**. The
vulnerability DB is cached in `data/trivy/cache` (shared with the compose
service), so the first scan downloads it and later scans run fast. The viewer
shows scanned target metadata and has a **Clear** button. Like Semgrep, the
script uses `docker run` (not `docker compose run`) so Windows drive-letter
paths mount correctly.

`TRIVY_SCANNERS` picks what to look for (default
`vuln,misconfig,secret,license` — drop `secret`/`license` for quieter reports).
Tighten with `TRIVY_SEVERITY` (comma list of `UNKNOWN,LOW,MEDIUM,HIGH,CRITICAL`),
`TRIVY_IGNORE_UNFIXED=1` (only actionable findings), and
`TRIVY_DETECTION_PRIORITY=comprehensive` (looser rootfs/ebpf detection — the
default is the precise mode). **`TRIVY_EXIT_CODE`** (e.g. `1`) makes the scan
exit with that code when anything is found — the report is still written first —
ready for CI gating. `TRIVY_VERSION` is pinned in `.env`.

## Code quality — SonarQube

**Profile:** `sonarqube` (`LDS_ENABLE_SONARQUBE`). **Off by default.**

A full code-quality platform (SonarQube Community Build): bugs, code smells,
duplications, coverage, and **quality gates** — broader than the security-only
Semgrep. Same viewer/scanner idea as Semgrep/Trivy, except the "viewer" is a
real server: the running **`sonarqube`** service (`sonarqube.test` /
`localhost:4544`, healthchecked) + a one-shot **`sonar-scanner`** image (own
`sonar-scanner` profile, never auto-starts).

```sh
lds tools sonar [path] [project-key]   # scan; key defaults to SONAR_PROJECT_KEY or the folder name
lds tools sonar token                  # create/refresh + print the analyzer token
lds tools sonar reset                  # lockout recovery: restore the admin/admin login
```

- Open **`sonarqube.test`** — **browsing needs no login** (see below). New
  projects are auto-created on the first scanner run (per-request project
  creation is on by default) or via the UI wizard.
- **No login to browse (default):** `SONARQUBE_FORCE_AUTH=false` disables forced
  authentication, so the UI (dashboards, issues, measures) opens anonymously —
  same spirit as DBX's open UI. It's read-only: settings, users and token
  management still require the `admin` login, and scans always authenticate with
  the scanner token. Flip `SONARQUBE_FORCE_AUTH=true` in `.env` to require a
  login for browsing too. (Once you toggle it in the UI it's persisted in the
  DB, which then wins over the env var — reset it under General settings >
  Security.)
- **Report export:** Community Build has no built-in report export (PDF reports
  are a commercial Governance/Enterprise feature) — the control panel serves a
  printable **full** report at **`http://localhost/sonar-report.php`** (also the
  "SonarQube report" card): pick a project → quality gate + conditions, ratings,
  every measure (grouped by domain), every issue (severity/type/rule/impacts/
  effort/status/tags/flows), all security hotspots, per-file metrics with
  totals, duplication groups, rule names and the analysis history, with
  **Print / Save as PDF** and **Download HTML**. It reads the Web API
  anonymously, so it needs no token/login as long as browsing needs no login.
  The layout mirrors the Semgrep report: stat tiles, bordered panels, a
  categories panel whose tag/rule chips filter, and a paged issues table whose
  rows expand into full detail (rule, impacts, flows, location, metadata).
  Filtering covers severity pills, type/rule selects, text search and clicks on
  any rule/file row; sorting is by severity, file or rule, and the active
  filters are written into the printed page.
- **Admin password:** on every `lds up sonarqube`, the `sonarqube-init` step
  reconciles the server's admin password with `SONAR_ADMIN_PASSWORD`: while the
  DB still has the initial `admin`, the value from `.env` is applied via the API
  (the policy wants **12+ chars incl. an uppercase letter**); if neither the
  `.env` value nor `admin` logs in, it warns instead of touching anything.
  Locked out after changing the password in the UI? `lds tools sonar reset`
  restores `admin`/`admin` with the documented recovery SQL and drops the cached
  token (the next scan recreates it).
- **Auth:** since SonarQube 26.10 the scanner refuses unauthenticated analysis
  and password basic auth is gone — the wrapper logs in through the Web API form
  (session cookie + `X-XSRF-TOKEN`), then calls `user_tokens/generate` (older
  servers fall back to basic auth). The token is cached at
  `data/sonarqube/token` and passed to the scanner. A `SONAR_TOKEN` from the
  env/`.env` wins only when **this** server accepts it — stale or foreign values
  (e.g. a global `SONAR_TOKEN` for another server) are ignored with a warning,
  and so is a stale cached token (recreated automatically). Refresh it with
  `lds tools sonar token`.
- **Server DB** is the shared Postgres (`lds_sonarqube` via
  `POSTGRES_INIT_SPECS`), so SonarQube needs the `postgres` profile running. The
  server binds `data/sonarqube/{data,logs,extensions}` (uid 1000 — on Linux those
  folders must be writable by that uid).
  `SONAR_ES_BOOTSTRAP_CHECKS_DISABLE=true` is set because Docker Desktop can't
  raise the Elasticsearch `vm.max_map_count` requirement; flip it to `false` on a
  native Linux host to enforce the check.
- Knobs in `.env`: `SONAR_SOURCES` (scan a subdir), `SONAR_EXCLUSIONS`,
  `SONAR_QUALITYGATE_WAIT=1` (scanner waits for the gate and exits `3` when it
  fails). `SONAR_PROJECT_KEY` fixes the key for every scan (else derived from the
  folder name) — only the value in `.env` counts: one inherited from the shell
  environment is ignored with a `note:`, since a stale terminal would otherwise
  silently retarget every scan. `SONARQUBE_MEM_LIMIT` caps the server (default 4g).
  Community Build limits: single branch, no PR decoration, no Rust analysis.

## Code intelligence — code-review-graph

**Profile:** `crg` (`LDS_ENABLE_CRG`). **Off by default.**

Local-first **AI code-intelligence graph** (`tirth8205/code-review-graph`):
Tree-sitter parses a repo into a persistent SQLite graph (functions, classes,
imports, calls), then answers blast-radius questions — "what's affected by this
change?" — so AI coding tools (Claude Code, Codex, Cursor, Gemini, Copilot, …)
read only the files that matter (~65× fewer tokens on reviews). The AI/MCP
integration is built in; the graph itself stays on your machine.

Same two-piece pattern as Semgrep/Trivy: a viewer (`crg` — what `lds up crg`
starts) + a one-shot scanner image (`lds/crg`, built from `configs/crg` —
upstream ships no official image).

```sh
lds up crg                    # start the report viewer (builds the scanner image too)
lds tools crg <path>          # build the graph + export the interactive HTML
lds tools crg <path> myapp    # custom name for the viewer URL (default: folder name)
lds tools crg clear           # clear all reports from the viewer
```

- **Viewer:** `http://crg.test/<name>/` (`localhost:4530`) — the interactive
  D3 force-directed graph (search, community legend, degree-scaled nodes).
  Landing page lists the report folders; `lds up crg` must be running.
- **Inside the scanned repo** the graph DB + HTML live in `.code-review-graph/`
  (auto-gitignored), so re-scanning the same repo is **incremental** — only
  changed files are re-parsed.
- **Local-first:** nothing is uploaded. The optional semantic-search embeddings
  and the MCP server run on your **host** if you want them:
  `pip install code-review-graph && code-review-graph install` (auto-configures
  every supported AI tool), or point your tool's MCP config at
  `docker run -v <repo>:/src -w /src lds/crg:2.3.7 serve` for the containerized
  endpoint.
- **Windows:** the script mounts the repo with a drive-letter path via `docker run`
  (the Compose `-v` colon-splitting caveat from Semgrep applies here too).

## Analytical query engines — DuckDB & Trino

**Profiles:** `duckdb` (`LDS_ENABLE_DUCKDB`), `trino` (`LDS_ENABLE_TRINO`). **Off
by default.** Two complementary analytical query engines for data exploration
and reporting.

### DuckDB — file engine (no network port)

Embedded OLAP engine running on the persistent **`lds/duckdev`** base image
(DHI alpine-base + DuckDB CLI binary). DuckDB is embedded like SQLite — no
server, no REST API. The `data.duckdb` file lives on a persistent named volume
shared with DBX for GUI access.

- **No network port:** DuckDB is not a server. Query it via `docker exec`:
  ```sh
  docker exec -it lds-duckdb duckdb /data/data.duckdb
  docker exec lds-duckdb duckdb -c "SELECT * FROM read_parquet('/data/sales.parquet') LIMIT 10" /data/data.duckdb
  ```

- **DBX connectivity:** the shared `duckdb-data` volume is also mounted at
  `/data` inside DBX, so its DuckDB driver opens the same `data.duckdb` file.
  Add a DuckDB connection in DBX pointing to `/data/data.duckdb` with
  **read-only** mode.

- **Data directory:** `data/duckdb/` on the host. Drop `.parquet`, `.csv`,
  `.json` files there. Inside the container they appear at `/data/`. Query them
  with `read_parquet('/data/filename.parquet')`.

- **Persistent database file:** The `data.duckdb` file lives on the Docker
  named volume `duckdb-data`. Survives restarts. Populate it:
  ```sh
  docker exec lds-duckdb duckdb /data/data.duckdb -c "CREATE TABLE sales AS SELECT * FROM read_parquet('/data/sales.parquet')"
  ```

- **Image:** `lds/duckdev:${DUCKDB_VERSION}` — built FROM DHI alpine-base,
  installs the official DuckDB CLI binary. Lightweight — `${DUCKDB_MEM_LIMIT}`
  (default `256m`).

- **Seed data:** Run `lds seed-data` to generate sample files into `data/duckdb/`.`

### Trino — `localhost:4451`

Full distributed SQL query engine with built-in web UI. Queries Parquet files
(via Hive connector with Hive Metastore), plus federated queries across MySQL,
Postgres, Kafka, and more. ANSI SQL, parallel execution, connector ecosystem.

- **Web UI:** `http://localhost:4451/ui` — query editor, query history, cluster
  overview.
- **JDBC:** Connect BI tools (Superset, Hop, Tableau) via Trino's JDBC driver.
  The connection string is `jdbc:trino://trino:8080/{catalog}/{schema}` (within
  the Docker network) or `jdbc:trino://localhost:4451/{catalog}/{schema}` (from the host).

#### Connecting Apache Superset to Trino

1. Start both profiles: `./lds.sh up superset trino`
2. Open Superset at `http://superset.test` (login `admin` / `admin`)
3. Go to **Data → Databases → + Database**
4. Choose **Trino** from the dropdown
5. Enter the **SQLAlchemy URI**:
   ```
   trino://trino:8080/hive/default
   ```
   (from the host, use `trino://localhost:4451/hive/default`)
6. Click **Test Connection** → **Save**

> The `trino` Python driver is auto-installed at Superset startup (installed
> into the writable `/app/pythonpath` since the venv is root-owned). No manual
> steps needed.

#### Connecting Apache Hop to Trino

Apache Hop connects to Trino via JDBC using the **Generic database** type. The
Trino JDBC driver (`trino-jdbc-483.jar`) is mounted into the Hop container from
the shared `assets/jdbc/` directory.

1. Fetch the driver once:
   ```bash
   curl -fsSL -o assets/jdbc/trino-jdbc-483.jar \
     https://repo1.maven.org/maven2/io/trino/trino-jdbc/483/trino-jdbc-483.jar
   ```
2. Start both profiles: `./lds.sh up hop trino`
3. Open Hop at `http://hop.test/ui`
4. In the **Metadata** perspective, right-click **Relational Database Connections**
   → **New**
5. Set:
   - **Connection Name:** `Trino`
   - **Connection Type:** `Generic`
   - **Access:** `Native (JDBC)`
   - **Driver Class:** `io.trino.jdbc.TrinoDriver`
   - **Custom Connection URL:** `jdbc:trino://trino:8080/hive/default`
6. Click **Test** to verify, then **Save**

- **Hive connector for Parquet:** Trino accesses Parquet files through the
  Hive Metastore. You register tables via `CREATE TABLE` SQL:
  ```sql
  CREATE TABLE hive.parquet_schema.sales (
    date DATE,
    product VARCHAR,
    revenue DOUBLE
  ) WITH (
    format = 'PARQUET',
    external_location = 'local:///data/trino/sales/'
  );
  ```

- **Sample data:** Trino ships with `tpch` and `tpcds` connectors for testing:
  ```sql
  SELECT * FROM tpch.tiny.orders LIMIT 10;
  ```

- **Federated queries:** Query across all LDS data sources in one SQL statement:
  ```sql
  SELECT * FROM tpch.tiny.orders o
  JOIN mysql.mysql_app.users u ON o.custkey = u.id;
  ```

- **Image:** Official `trinodb/trino:${TRINO_VERSION}`.
- **Metastore:** `hive-metastore` (official `apache/hive:4.2.1` image),
  auto-started with the `trino` profile. Backed by the shared LDS Postgres
  (`lds_hive_metastore` database).

- **Data directory:** `data/trino/` — Parquet files for Trino to query.

- **Caps:** `${TRINO_MEM_LIMIT}` (default `2g`).

### Keycloak — `auth.test`

**Profile:** `keycloak` (`LDS_ENABLE_KEYCLOAK`). **Off by default.** Run
`lldap` alongside it — the imported realm federates that directory.

One OIDC/OAuth2 issuer for every project instead of a bespoke login per app.

- Admin console: `auth.test` — `admin` / `KEYCLOAK_ADMIN_PASSWORD` (default
  `admin`). Open it at exactly the origin pinned in `KEYCLOAK_PUBLIC_URL`
  (`https://auth.test` with HTTPS on, `http://auth.test` otherwise): the
  console's third-party-cookie check iframe is built from that URL and its CSP
  is `frame-src 'self'`, so browsing from any other origin (including the raw
  `localhost:4546` port) blocks the frame and keycloak.js throws
  *"Timeout when waiting for 3rd party check iframe message."* With HTTPS on,
  `http://auth.test` is 301-redirected to `https://auth.test`, so the dashboard
  link and a typed URL both land on the pinned origin.
- Issuer: `KEYCLOAK_PUBLIC_URL` + `/realms/lds` (e.g.
  `https://auth.test/realms/lds` with HTTPS on), pinned by `KC_HOSTNAME` so the
  same value works through the proxy, on `localhost:4546`, and inside
  `lds-network` (`http://keycloak:8080` for server-to-server calls)
- Clients from the imported realm: **`lds-web`** (public SPA, PKCE S256, any
  `*.test` / `localhost` redirect) and **`lds-api`** (confidential, secret
  `KEYCLOAK_API_CLIENT_SECRET`, service accounts enabled)
- Realm roles: `admin`, `developer`, `viewer`
- **User federation:** the realm points at `ldap://lldap:3890`
  (`ou=people,<base DN>`, `uid` as username and UUID, READ_ONLY, import on first
  login), so a password is checked against the directory — Keycloak never owns
  the users. Create one in LLDAP, then sign in with it at any client.

- **Sync:** `importEnabled=true` copies a directory user into Keycloak on their
  first login, and `fullSyncPeriod=300` (seconds, in
  `configs/keycloak/import/lds-realm.json`) runs a full sync every 5 minutes — so
  users you create in LLDAP or OpenLDAP show up in the admin console without
  waiting for a login. *Sync all users* (User federation → `lldap`) pulls them in
  immediately. The realm is imported on first boot only: after editing it, run
  `lds rm keycloak && lds up keycloak` (and wipe the `lds_keycloak` database if
  the realm already exists — `--import-realm` skips existing realms).
- Realm source: `configs/keycloak/import/lds-realm.json`, imported on the first
  boot only. After editing it: `lds rm keycloak && lds up keycloak`.
- Metadata: the shared Postgres (`lds_keycloak` via `POSTGRES_INIT_SPECS`), so
  clients and sessions survive restarts. `start-dev` is deliberate (local HTTP)
  but still uses Postgres, not the H2 dev file.
- `KC_BOOTSTRAP_ADMIN_*` (not the old `KEYCLOAK_ADMIN*`) creates the admin, and
  only on an empty database.

  7-day retention in the `loki-data` volume. Loki is **headless: it has no web
  UI**, so `loki.test/` redirects to Grafana Explore with the Loki datasource
  already selected (its API paths — `/ready`, `/metrics`, `/loki/api/v1/*` —
  still hit Loki directly).
- **Alloy** (`grafana/alloy`) — tails every container's stdout/stderr through the
  Docker socket and pushes to Loki. It is Promtail's successor (Promtail reached
  EOL in March 2026) and needs no per-project config: any `docker compose up`
  shows up in Grafana seconds later, labelled with `container`, `stream` and
  `compose_project`.
- **Tempo** (`grafana/tempo`) — trace store at `tempo.test` / `localhost:4548`,
  24h retention, OTLP in on `4317`/`4318`. Tempo is headless too: `tempo.test/`
  redirects to Grafana Explore with the Tempo datasource selected, and its API
  paths (`/ready`, `/api/*`) reach Tempo unchanged.
- **OpenTelemetry collector** — the ONE endpoint an app should send to:
  `OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318` from the host, or
  `http://otel-collector:4318` from a container. It fans traces to Tempo, logs
  to Loki and metrics to Prometheus remote-write, so instrumentation is one env
  var per app.

### SonarQube MCP

**Profile:** `sonarqube` (comes with the SonarQube server — `lds up sonarqube` or
`LDS_ENABLE_SONARQUBE=true`). **Off by default.**

The official SonarSource MCP server is a second container that sits alongside the
SonarQube server and lets AI tools — **Zed** (see below), Claude Code, Cursor,
Codex, Windsurf etc. — query this stack's SonarQube without leaving the editor.

- **Image:** `sonarsource/sonarqube-mcp` (Sonar Source-Available License 1.0 — NOT
  an OSI open-source licence; documented in <a href="18-credits.md">§ Credits</a>).
- **Transport:** Streamable HTTP, loopback only.
- **URL:** `http://127.0.0.1:${SONARQUBE_MCP_HOST_PORT:-4549}/mcp`
  (direct loopback for the editor tool — see the Zed setup below).
- **Host name:** `sonarqube-mcp.test` is also served through the proxy (`CERT_NAME`),
  so the MCP URL works from inside the network too.
- **Auth:** Bearer token via `SONARQUBE_TOKEN` (set from `${SONAR_TOKEN}` in `.env`).
  The server auto-discovers your SonarQube **analyzers** and the language plugins
  available on the server, so the tool exposes the matching issue/rules/measures.
- **Read-only:** the container runs with `SONARQUBE_READ_ONLY=true` — editor agents
  can inspect issues but not change issue status.
- **Health:** `http://127.0.0.1:4549/health` (the only unauthenticated endpoint).

Zed setup (one-time, in `%APPDATA%/Zed/settings.json` on Windows, or `~/.config/zed/settings.json` on other platforms):

```json
{
  "context_servers": {
    "sonarqube": {
      "url": "http://127.0.0.1:4549/mcp",
      "env": {
        "SONAR_TOKEN": "<paste the value of SONAR_TOKEN from .env here>"
      }
    }
  }
}
```

`SONAR_TOKEN` is the same user token `/sonar-report.php` uses (My Account →
Security, or `lds tools sonar token` creates one). Zed reads it from the config
at startup; the MCP server validates it against the SonarQube server. Leave it
empty and the connection returns `401 SonarQube token required`.

An example Zed setting for a Windows host is already in the runtime Zed config
at `C:\Users\Lenovo\AppData\Roaming\Zed\settings.json` — the live value of
`SONAR_TOKEN` there is the `lds-scanner` token from `.env` (or update it to a
fresh `lds-zed-mcp` token if you prefer separate tokens for scanning and the
editor).

Start it: `lds up sonarqube` (the MCP container is in the same profile).
Verify: `curl -sS -m 15 -X POST http://127.0.0.1:4549/mcp`
`-H 'Content-Type: application/json'` `-H 'Accept: application/json,text/event-stream'`
`-d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"verify","version":"1.0"}}}'`
should return `200` + `{"result":{"capabilities":…` — not a `401`.

Tips: the MCP server needs the SonarQube server healthy first (`depends_on`),
so on a cold start give it ~30 s. If Zed's assistant can't reach it, confirm
`lds ps` shows `lds-sonarqube-mcp` **healthy**.

Every service is mem-capped and its version is pinned in `.env`
(`LOKI_VERSION`, `TEMPO_VERSION`, `ALLOY_VERSION`, `CADVISOR_VERSION`,
`NODE_EXPORTER_VERSION`, `OTEL_COLLECTOR_VERSION`). Loki, Tempo and the
collector are distroless images with no shell, so they carry **no in-container
healthcheck** — Prometheus scrapes them, and Grafana shows a dead datasource
immediately if one fails.

## Search — Meilisearch

**Profile:** `search` (`LDS_ENABLE_SEARCH`). **Off by default.**

Typo-tolerant, as-you-type search and faceting — the small alternative to
OpenSearch/Elasticsearch when you just need fast "find as I type".

- API: `meili.test` / `localhost:4545` — **no web UI**, it is a JSON API
- Auth: `Authorization: Bearer $MEILISEARCH_MASTER_KEY`
  (default `lds-dev-meili-master-key-change-me`); without it you get `401`
- Health: `GET /health` → `{"status":"available"}`
- Data: `data/meilisearch` (LMDB index + dumps)
- License: MIT **Community Edition** only — the BUSL-1.1 Enterprise Edition is
  not enabled, so no SSO/sharding features

```bash
K=lds-dev-meili-master-key-change-me
curl -X POST -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '{"uid":"docs","primaryKey":"id"}' http://localhost:4545/indexes
curl -X POST -H "Authorization: Bearer $K" -H 'Content-Type: application/json' \
     -d '[{"id":1,"title":"Hello search"}]' http://localhost:4545/indexes/docs/documents
curl -H "Authorization: Bearer $K" http://localhost:4545/indexes/docs/search \
     -H 'Content-Type: application/json' -d '{"q":"helo"}'
```

## Built-in utilities — LDS Text Diff & LDS Palette Generator

No profile and no containers — two static pages served straight from the
control panel's own document root (`configs/web/dashboard/tools/`, mounted
read-only into `lds-php`):

- **LDS Text Diff** — `http://localhost/tools/diff/` — side-by-side rich-text
  comparison: type or paste HTML in both panes; lines are diffed (LCS) and
  changed words are highlighted (green insertions, red deletions). One
  self-contained file, no JS dependencies.
- **LDS Palette Generator** — `http://localhost/tools/palette/` — Coolors-style
  color boards: harmony modes (random, analogous, complementary, triadic,
  tetradic, monochromatic), per-column lock, click-a-column-to-copy HEX,
  H/S/L fine-tuning with WCAG contrast hints, HEX/RGB/HSL/CSS-var exports,
  `Space` regenerates, the palette is remembered in `localStorage`.

They show up on the control panel under *Developer utilities* and *Design*
without a reachability dot — they can't be down while the panel itself
renders.
